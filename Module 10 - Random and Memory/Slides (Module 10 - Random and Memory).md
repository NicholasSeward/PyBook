## Key Terms

**Pseudorandom** - Numbers that appear random but are generated by a deterministic algorithm

**True Random** - Numbers generated from unpredictable physical processes like radioactive decay

**Seed** - A starting value that determines the sequence of pseudorandom numbers

**Aliasing** - Multiple variables pointing to the same object in memory

**Shallow Copy** - A copy that creates a new object but shares nested objects

**Deep Copy** - A complete copy that creates independent copies of all nested objects

**Time Complexity** - How an algorithm's runtime grows with input size (Big O notation)

**Space Complexity** - How much memory an algorithm uses as input size grows

**Benchmarking** - Measuring and comparing the performance of different code approaches

**Reference** - A pointer to an object's location in memory

## Random vs Pseudorandom

### What is Random?
Random means **unpredictable** - you can't guess what comes next. In programming, we often need random numbers for:
- **Games** and entertainment
- **Simulations** and modeling
- **Security** and cryptography
- **Testing** with varied data

### Pseudorandom Numbers
- **Generated by computers** using mathematical formulas
- **Look random** but follow a predictable pattern
- **Reproducible** when using the same seed
- **Fast and efficient** for most applications
- **Python's random module** uses pseudorandom generation

### True Random Numbers
- **Generated from physical processes** in the real world:
  - Radioactive decay (timing of particle emissions)
  - Atmospheric noise (static in the air)
  - Thermal noise (random movement of electrons)
  - Quantum effects (behavior of tiny particles)
- **Completely unpredictable** and cannot be reproduced
- **Essential for cryptography** and security applications

### Why Pseudorandom?
- **Same seed** = same sequence every time
- **Different seed** = different sequence
- **Useful for testing** - get same "random" results
- **Good for games** - predictable but still fun

## Random Module Functions

### Basic Random Functions
- **`random.random()`** - float between 0.0 and 1.0
- **`random.randint(1, 10)`** - integer between 1 and 10
- **`random.choice(fruits)`** - pick random item from list

### Advanced Random Functions
- **`random.shuffle(cards)`** - mix up a list
- **`random.sample(students, 3)`** - pick 3 random items
- **`random.randrange(0, 100, 5)`** - random multiple of 5

### Setting the Seed
- **`random.seed(42)`** - start with same sequence
- **Same seed** = same random numbers every time
- **Good for testing** and debugging
- **Different seed** = different sequence

## Memory Concepts

### Stack vs Heap Memory
- **Stack Memory**
  - **Automatic allocation** and deallocation
  - **Fast access** and predictable size
  - **Stores local variables** and function calls
  - **LIFO structure** (Last In, First Out)
  - **Limited size** and scope

- **Heap Memory**
  - **Dynamic allocation** and deallocation
  - **Slower access** but flexible size
  - **Stores objects** and complex data structures
  - **Manual management** in some languages
  - **Larger size** and global scope

### Python Memory Management
- **Variables** are stored on the stack
- **Objects** are stored on the heap
- **Variables point to** objects in memory
- **Function calls** use the stack

## References and Aliasing

### How References Work
- **Variables point to** objects in memory
- **Multiple variables** can point to same object
- **Changing one affects** the other
- **Use `is` to check** if same object

```python
# Aliasing example
a = [1, 2, 3]
b = a  # b points to same list as a

print(f"a: {a}")      # [1, 2, 3]
print(f"b: {b}")      # [1, 2, 3]
print(f"a is b: {a is b}")  # True - same object

# Change through b
b[0] = 99
print(f"After change:")
print(f"a: {a}")      # [99, 2, 3] - a also changed!
print(f"b: {b}")      # [99, 2, 3]
```

### Aliasing Problems
- **Functions receive references** to objects
- **Modifying inside function** affects original
- **Can cause unexpected bugs** if not careful
- **Need to copy** if you don't want changes

### Why Aliasing Matters
- **Multiple variables** can control the same object
- **Unexpected side effects** when modifying shared data
- **Hard to debug** because changes appear in unexpected places
- **Common source of bugs** in Python programs

## Copying Objects

### Shallow Copy
- **`copy.copy(original)`** creates new top-level object
- **Nested objects are shared** between original and copy
- **Changing nested object** affects both
- **Faster and uses less memory**

### Deep Copy
- **`copy.deepcopy(original)`** creates completely independent copy
- **All nested objects** are copied too
- **Changing nested object** only affects the copy
- **Slower but completely safe**

### When to Use Each
- **Shallow Copy** (`copy.copy()`)
  - Simple data structures
  - When you want to share nested objects
  - Faster and uses less memory

- **Deep Copy** (`copy.deepcopy()`)
  - Complex nested structures
  - When you need complete independence
  - Slower but completely safe

## Time Complexity

### Big O Notation Basics
- **O(1)** - Constant time (same time regardless of input size)
- **O(n)** - Linear time (time grows proportionally with input)
- **O(log n)** - Logarithmic time (time grows slowly)
- **O(n²)** - Quadratic time (time grows rapidly)
- **O(2ⁿ)** - Exponential time (time grows extremely rapidly)

### Common Time Complexities
- **O(1)** - Getting first item from list (always fast)
- **O(n)** - Finding item in list (time grows with size)
- **O(n²)** - Checking all pairs (nested loops, very slow)

### Business Impact
- **O(1)**: Whether you have 100 or 1 million users, it's always fast
- **O(log n)**: Even with 1 billion users, it's still very fast
- **O(n)**: Acceptable for most business needs
- **O(n²)**: Avoid in business applications - costs money and customers

---

## Space Complexity

### Memory Usage Analysis
- **O(1)** - Constant space (same memory regardless of input)
- **O(n)** - Linear space (memory grows proportionally with input)
- **O(n²)** - Quadratic space (memory grows rapidly)

### Space Complexity Examples
- **O(1)** - Adding two numbers (few variables)
- **O(n)** - Creating list of size n
- **O(n²)** - Creating n×n matrix

### Memory vs Time Trade-offs
- **Recursive functions** - use less memory but slower
- **Iterative functions** - use more memory but faster
- **Choose based on** your needs

## Common Algorithms

### Max and Min Functions
- **Check each number** in the list
- **Remember the best** value seen so far
- **O(n) time** - grows with list size
- **O(1) space** - only use a few variables

### Linear Search
- **Check each item** one by one
- **Return position** when found
- **Return -1** if not found
- **O(n) time** - grows with list size

### Binary Search
- **Requires sorted list** to work properly
- **Check middle item** and eliminate half
- **Very fast** - O(log n) time
- **Good for large lists** where sorting is worth it

## Time Module and Benchmarking

### Basic Time Functions
- **`time.time()`** - get current timestamp
- **`time.ctime()`** - get readable time
- **`time.perf_counter()`** - most precise timing

### Performance Benchmarking
- **Measure start time** before code
- **Measure end time** after code
- **Calculate difference** to get elapsed time
- **Compare approaches** to see which is faster

### Comparing Different Approaches
- **Test loop approach** vs list comprehension
- **List comprehension** is usually faster
- **Always measure** - don't guess which is faster
- **Use `time.perf_counter()`** for best accuracy

## Dos and Don'ts

### ✅ DO:
- **Use `random.seed()`** when you need reproducible results for testing
- **Choose appropriate copy method** (shallow vs deep) based on your data structure needs
- **Consider time and space complexity** when designing algorithms for large datasets
- **Benchmark your code** to compare different approaches before optimizing
- **Use `time.perf_counter()`** for precise timing measurements
- **Handle aliasing carefully** to avoid unexpected side effects
- **Document complexity** of your algorithms for future developers

### ❌ DON'T:
- **Use random numbers for cryptography** (use `secrets` module instead)
- **Assume shallow copy is sufficient** for complex nested structures
- **Ignore complexity analysis** when working with large datasets
- **Use `time.time()`** for precise benchmarking
- **Modify objects** passed as parameters without documenting it
- **Create unnecessary copies** that waste memory
- **Optimize prematurely** without measuring first
